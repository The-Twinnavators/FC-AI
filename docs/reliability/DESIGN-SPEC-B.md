# Design-spec application: path and regression evidence (part B)

This is a pipeline regression, not a claim that either design is good. Research is not involved.

## Path

| Stage | Where | What it does |
|---|---|---|
| Selected style or approved direction → spec | `workspace/designSpec.ts` `DesignSpec` | A versioned record: typography, scale, palette, density, surface style, radii, border, content width, composition changes, signature, responsive notes, sources. |
| Spec checks | `specProblems` | Refuses:<br>• fonts FlowCode doesn't bundle;<br>• colour pairs below WCAG AA;<br>• corners over 12px;<br>• unknown surface styles;<br>• a surface style whose fixed outline width contradicts the spec's border width (reported, not resolved). |
| Runtime token application | `applyDesignSpec` | Applies the surface style first, then the spec's tokens (the spec wins). It reuses the Styles page's existing token writer and surface-style code. |
| Bounded coder work | `applyDesignSpec().coderWork` | Each coder requirement, with the files it touches. This is only a change list; nothing is claimed as deterministic. |
| Rendered verification | `quality/designSpecCheck.ts` | `measureDesign` reads computed styles: the page, the first visible heading, a card, and root tokens resolved in the page. `specImplementation` gives each requirement a status. Text content is never read. |
| Human visual approval | `SpecApplication.humanApproval` | Always starts `pending`. Implementation evidence never sets it. |

## Responsibility per requirement

| Requirement | By | How it is verified |
|---|---|---|
| type-families | tokens (`--font-display`, `--font-sans`) | The rendered heading and text families. |
| type-scale (hierarchy) | tokens (`--text-*`, `--heading-weight`) | Tokens plus the rendered heading weight. |
| palette | tokens (`--color-*`) | The rendered page background, the content colour and the accent token. |
| density | tokens (`--space-1..9`) | Tokens; a card's padding is reported as evidence. |
| shape | tokens (`--radius-*`, `--border-width`, `--surface-radius`) | Tokens plus the rendered card's corners and outline. |
| surfaces | tokens (the surface style) | The style's tokens resolved in the page; a card's shadow is reported as evidence. |
| content-width | tokens (`--content-max`) | The token. |
| heading-case (capitals) | coder | `text-transform` on the rendered heading. Until then it is "for the coder". |
| composition-*, signature, responsive-* | coder | Not visible in styles. "For the coder" until done, then "needs your review". Never "implemented". |
| Any token the app doesn't declare | unsupported | Shown as "not implemented", naming the missing tokens. Never silently "applied". |

## Evidence

Both specs were applied to separate copies of the same app: the Clean Cart slice's app (eval 1), regenerated by FlowCode as in `functional-journey.test.ts`. The specs are fixtures in `packages/daemon/test/fixtures/design/`:
- **Field Notes:** editorial, airy, flat.
- **Bold Aisle:** condensed capitals, compact, neo-brutalist.

The test is `design-spec-render.test.ts`, with measurements in `design-spec/evidence.json`.

| Dimension | Field Notes | Bold Aisle |
|---|---|---|
| Typography | Playfair Display / Literata | Oswald / DM Sans |
| Hierarchy | h1 64px over 13px text, weight 700 | h1 25.6px over 14.2px text, weight 600 |
| Density | card padding 15.6px | card padding 9.6px |
| Surface | corners 4px, 1px outline, no shadow | corners 0px, 3px outline, 6px hard shadow |
| Palette | page #f6f1e7, text #2a2118 | page #fff3c4, text #111111 |
| Token requirements | 7/7 implemented | 7/7 implemented |
| Coder requirements | 3 "for the coder" | 4 "for the coder" (including capitals) |
| Functional journey (16 steps) | passes | passes |

**Text-only control.** The same app had only a heading's words changed and no spec applied. Measured against Bold Aisle:
- 0 token requirements were implemented;
- the coder requirements stayed "for the coder";

## Found and fixed on the way

**FlowCode's library.** `templates/library/css/lookupframe.css` gave the frame's page headings (`.fl-lkf-hero h1`, `.fl-lkf-later h1`, `.fl-lkf-demo-page h1`) no `font-weight`. They rendered in the browser's default bold whatever the heading-weight token said. They now read `--type-h1-weight` / `--heading-weight`. The verification caught this: spec B's tokens were right, but the rendered heading wasn't.

**Spec rules.**
- The surface style is applied before the spec's tokens. Some styles set their own heading weight and card corners, which would otherwise override the spec.
- Small text keeps a 13px floor however steep the scale. The expressive scale had put it at 11.3px.

## Limitations

- **Single sample.** The measurement takes one heading, one card and one text sample, on Home at 1280px. It is not a full-page or responsive audit.
- **Coder work.** Composition, signature and responsive changes are listed but not executed or verified here. Coder execution, and its cost, still needs measuring.
- **Starter defaults.** A spec matching the starter's own defaults (for example flat surfaces) reads as implemented without any change. That is correct, but it isn't evidence that anything was applied.
- **Tokens only.** Only token-reading rules follow a spec. Library rules that hard-code weights or sizes (like the frame headings above) only show up when a check looks at them. No library-wide audit was done.
- **Not yet wired into FlowCode.** Spec generation from a selected style or direction, wiring into a build step, a UI and the approval record are not built.
